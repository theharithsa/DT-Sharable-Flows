What is the Model Context Protocol?

An open standard that lets an AI assistant call real systems through a defined, permissioned set of tools — instead of guessing from training data.

The assistant never touches your cluster directly. It can only do what the MCP server's tools allow — nothing more.
Act 1 · concept 2 of 4

Introducing the Dynatrace Managed MCP Server

  • Built for Managed — targets the v2 REST APIs on your self-hosted cluster, not Grail or DQL
  • Official open source — dynatrace-oss project, MIT licensed, community-supported via GitHub Issues
  • No extra licensing cost — queries incur nothing beyond your standard Managed license
  • Simple install — npx -y @dynatrace-oss/dynatrace-managed-mcp-server@latest
What it needs
  • Dynatrace Managed 1.328.0 or newer
  • API endpoint URL + environment ID + alias per environment
  • An API token with read scopes
Act 1 · concept 3 of 4

Two connection modes — pick per team, not per company

Local mode
  • Runs on your machine, launched by your IDE or assistant via npx
  • Credentials live in your local config only
  • Great for individual development & testing
  • Zero infrastructure — working in minutes
Remote mode (HTTP/SSE)
  • Centrally hosted once, shared by the whole team
  • Per-user tokens passed per request
  • No shared credentials stored on the server
  • The governed path for team-scale rollout

Start local to prove value in a day. Move to remote when more than a handful of people want in.

Act 2 · the hybrid story

Runs side by side with the SaaS MCP

Migration scenario

Moved to SaaS but historical data still lives on Managed? Configure both MCP servers in one client — the assistant queries Managed for history and SaaS for live data.

Tandem scenario

Some apps on Managed, others on SaaS? One conversation spans both — with rule files steering the assistant to the right server per system.

Key differences: the SaaS MCP speaks DQL + OAuth + Davis CoPilot; the Managed MCP speaks v2 APIs + API tokens. Name the two servers differently and add steering rules so the assistant never guesses.

Act 3 · take it home

Getting started — before your coffee cools

Step 1

Create a read-scoped API token

DataExport, problems.read, securityProblems.read, entities.read, slo.read, logs.read, metrics.read, events.read, auditLogs.read, networkZones.read
Step 2

Write a config file, add the server

dt-config.yaml — API endpoint URL, environment ID, alias, apiToken: ${DT_PROD_TOKEN} — then npx -y @dynatrace-oss/dynatrace-managed-mcp-server@latest in .vscode/mcp.json
Step 3

Ask your first question

“What problems has Dynatrace identified? Give details of the first problem.”
Use ${VAR_NAME} interpolation in the config file — commit it to version control with zero secrets inside. Works in VS Code, Claude Desktop, Cursor, Kiro, Windsurf, and Gemini CLI.
Act 3 · scaling it safely

Guardrails for the team rollout

  • Move to remote mode (HTTP/SSE) once more than a few users are in — per-user tokens per request, nothing stored server-side
  • Run the HTTP server behind TLS — it binds 127.0.0.1 and does not terminate TLS itself
  • Built-in rate limiting protects your cluster — default 20 tool calls per 20 seconds, tunable via DT_MCP_RATE_LIMIT_*
  • Keep queries narrow — specific time ranges (now-1h) and entity selectors, per the repo's performance guidance
  • Add a rule file naming each environment alias — the assistant should never guess which cluster you mean
  • It is community-supported — file issues and ideas on GitHub, and contribute back what you build
